## Why this project exists

Prior projects (ShopFlow — e-commerce microservices, SkyCheck — hackathon AI inspection tool,
ZeroHour — multi-agent productivity app) already demonstrate full-stack CRUD, auth, and AI-API
integration. TriageNet exists specifically to demonstrate **algorithmic depth** — priority
scheduling, bipartite matching (Hungarian algorithm), graph shortest-path/max-flow, and a small
offline-trained ML scoring model — applied to a real operational problem (healthcare resource
allocation), not another CRUD app. That differentiation is the entire point of the project;
do not let it collapse back into "just another Spring Boot CRUD app with a dashboard."

## Non-negotiable priorities (in order)

1. **The four algorithms must be real, hand-implemented, and correct** — severity scoring,
   priority queue with decay, Hungarian algorithm, Dijkstra (+ optional MCMF). These are the
   entire value proposition of the project. Do not substitute a library call or a trivial
   greedy shortcut for these without flagging it explicitly to Priyanshu first.
2. **Deployability by end of Week 4.** A working, deployed system with 3 dashboard views beats
   a more ambitious system that only runs locally.
3. **Explainability.** Every algorithmic output (a score, an assignment, a routing decision)
   should be traceable — this matters enormously for the viva/interview defense of the project.
4. Everything else (extra dashboard polish, stretch features) is secondary to the above three.

## Tech conventions carried over from prior projects

- Backend: Spring Boot, layered architecture (controller → service → repository), Spring
  Security + JWT for auth, Spring Data JPA + Hibernate, PostgreSQL.
- Frontend: React (Next.js), component-first, keep visualization libraries lightweight
  (Recharts/D3 for the graph view — no heavyweight mapping SDKs needed since hospitals are
  simulated, not geolocated in the real world).
- Docker for both backend and frontend; deploy backend to Railway/Render, frontend to Vercel
  — this matches ShopFlow's existing deployment pattern.
- **Security hardening habit**: no hardcoded credentials or secrets in source — always
  environment variables, following the same fix already applied on ShopFlow.
- Claude (this assistant) is used for strategic direction, architecture, prompt engineering for
  Antigravity, and content drafting (PRD/TRD/reports/pitch material) — not for writing the
  actual implementation code. Antigravity does the vibe-coding/implementation work directly
  from these docs.

## Known constraints

- No real hospital dataset — all hospital/resource/patient data is generated by the Scenario
  Simulator module described in the TRD. Don't try to source or scrape real hospital data.
- The ML severity-scoring model is trained **offline, once**, in Python against a public
  dataset, and only the resulting coefficients are embedded in the Java service. There is no
  live Python inference service in this architecture — don't introduce one.
- This is explicitly framed (in the report and viva) as a simulation/demonstration system, not
  a clinically validated product. Don't over-claim real-world readiness in generated copy.

## Things that should NOT change without an explicit decision

- The four core algorithms and their general approach (priority queue with decay, Hungarian
  assignment, Dijkstra/MCMF routing, offline-trained severity scorer).
- The 5-week phased plan in the PRD (schema/auth → scoring/triage → assignment → routing →
  dashboard/polish).
- The 3-view dashboard scope (capacity view, queue view, regional graph view) — resist adding
  a 4th view mid-build.
